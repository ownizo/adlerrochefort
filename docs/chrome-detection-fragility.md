# Chrome detection fragility — history, fix, and what's still open

**Repo:** `ownizo/adlerrochefort`. **Branches involved:** `chore/chrome-sweep`,
`chore/thankyou-chrome-dedupe`, `fix/chrome-detection` (chrome detection,
merged), `docs/langswitcher-drift` (the lang-switcher addendum below). Written
so the next person who hits one of the still-open items has the diagnosis
instead of rediscovering it.

## The bug

`scripts/unify-chrome.mjs` used to detect an existing topBar/footer/back-link
by matching a *literal* attribute string: `class="asf-top-bar"` exactly, a
bare `<footer>` exactly, `class="nav-back"` immediately after `href="..."`
exactly. Any element carrying an **additional** class — `class="asf-top-bar
on-dark"`, `<footer class="on-dark">` — read as having none at all. The
script's gap-fill pass then inserted a second one next to the real one.

Two distinct incidents, found in the same session, four months apart in
origin:

- **The eleven Dutch cluster pages** (`scripts/generate-nl-cluster.mjs`) carry
  a genuine topBar and footer, styled `on-dark`. Running the sweep on them
  (confirmed by actually running it and inspecting the diff, not assumed)
  duplicated both.
- **Three "thank you" pages** — `/obrigado/`, `/en/thank-you/`,
  `/nl/bedankt/` — already had two topBars and two footers each, predating
  either branch above. `git blame` showed the `on-dark` chrome was original
  (Jul–Aug 2026) and the plain-classed duplicate was inserted *later* by a
  `netlify[bot]` commit — an earlier version of this same exact-string blind
  spot, working in the opposite direction: it kept "refreshing" a legacy
  fragment it could still see while the real chrome sat next to it, invisible.

The three thank-you pages were deduplicated by hand, page by page, no
script — three pages didn't need one, and the automated pass is what created
the risk of making it worse. Verified beyond HTML parsing: served `public/`
locally and viewed all three in a browser.

## The fix

`scripts/unify-chrome.mjs` now matches structurally: `matchElement(html, tag,
{ className })` finds the element by tag name, and — only where the tag alone
doesn't identify the role — a class *token*, tolerant of whatever else rides
along on the attribute and in whatever order. `class="asf-top-bar"` and
`class="asf-top-bar on-dark"` and `class="on-dark asf-top-bar"` all resolve as
one top bar; `class="asf-top-bar-secondary"` correctly does not match
`"asf-top-bar"` — a token match, not a substring one. The same helper covers
the article back-link's `class="nav-back"` check, which had the identical
literal-string exposure (not yet triggered by any page, fixed anyway).

Verified, not assumed: `--dry-run` reports zero across the site;
a real (non-dry-run) sweep in an isolated `git worktree`, with the SKIP
exclusions below temporarily lifted, produced zero duplication across all
fourteen previously-affected pages, and left every bespoke topBar's text
untouched (the existing content gate — only replace a topBar whose text
matches a campaign-CTA pattern — still does its job now that it can see what
it's gating).

## Why the fourteen pages are still excluded — and it's not the bug anymore

Fixing detection surfaced a second question, separate from detection: footer
replacement has no content gate the way topBar's does — it never needed one,
because until now it could never see a suffixed footer to begin with. With
that blind spot gone, the sweep's footer replacement will cheerfully overwrite
*any* footer it finds with the sitewide one, including these fourteen pages'
own.

That would have been a real regression, not a fix:

- The **Dutch cluster's** footer is generated by, and matches, the cluster it
  belongs to — its own design system (`ar-nl.css`), not a stand-in for the
  sitewide one.
- The **thank-you pages'** footer is purpose-built, with its own inline
  `<style>` block, for a page whose only job is to confirm a submission
  landed — deliberately not six columns of navigation competing for a
  visitor's attention the moment after they've converted. The institutional
  footer there is a UX regression, not normalisation.

Both are excluded in `scripts/unify-chrome.mjs`'s `SKIP` list now for that
reason — the same category `/de/`, `/fr/` and the Spain cluster already were:
a chrome of their own, not a gap to fill. The comments in that file say so
directly and no longer mention the detection bug as the reason, because it
isn't one any more. Worth recording plainly here too: the detection bug had
been *accidentally* protecting both groups' footers from ever being touched.
Fixing detection without also making this call would have converged all
fourteen to the sitewide footer silently, the first time anyone ran the real
sweep.

**`check:freshness` after this fix:** the exclusion takes all fourteen pages
cleanly out of scope, not just quietly out of sight — `SKIP` removes them
from `unify-chrome.mjs`'s own file list before either pass runs, so there is
nothing left for `check-generator-freshness.mjs`'s delegated `--dry-run` call
to report on them. `chrome-partials-gaps`, the WARN category that fired while
these fourteen sat in scope with the bug unfixed, is gone from the report
entirely. Confirmed by running the checker after the change and reading its
own count, not inferred.

## The same exact-string assumption, found elsewhere — not fixed here

Checked whether the same assumption exists elsewhere in `scripts/`. It does,
in three places that read/detect existing chrome rather than emit it fresh.
None touched in this branch — recorded here so whoever hits one has the
diagnosis rather than rediscovering it:

- **`scripts/lib/partials.mjs:67,70`** — `between(src, '<div
  class="asf-top-bar">', '</div>', opt)` and `between(src, '<footer>',
  '</footer>', opt)` extract the canonical chrome *from* the three source
  homepages (`public/index.html`, `public/en/index.html`,
  `public/nl/index.html`) using the same literal-string approach. Currently
  safe — checked: all three source homepages currently use plain, unsuffixed
  `class="asf-top-bar"` and `<footer>` — but latently fragile the same way if
  that ever changes.
- **`scripts/build-location-articles.mjs:249`** — `html.indexOf('<footer>',
  relStart)`, used to find an insertion point in a page's existing footer.
  Same assumption, different context: a generator inserting into individual
  articles rather than a sweep across the whole site.
- **`scripts/internal-links.mjs:433`** — `'<footer>'` listed as one of two
  literal anchor strings used to locate an insertion point.

One existing script already handles this defensively, and is worth pointing
at as the pattern to follow rather than unify-chrome.mjs's original approach:
**`scripts/add-spain-footer-links.mjs`** looks for the first bare `<footer>`
tag and, when it isn't found, `SKIP`s the file and logs an error for
by-hand inspection — rather than silently doing nothing (unify-chrome.mjs's
old gap-fill behaviour) or silently duplicating (what that silent nothing
turned into once a second pass was added later). Neither
`build-location-articles.mjs` nor `internal-links.mjs` has that safety net
today.

## Lang-switcher drift on the Dutch cluster — diagnosed, not fixed

This is a different bug from the exact-string chrome detection above. It
belongs in this file because it is the same *kind* of problem: two sources of
truth for the same chrome, and regenerating one silently undoes the other.

### What diverged

Every page's language control has one canonical writer:
`scripts/lang-switcher.mjs`. It reads confirmed language pairs and writes the
nine-language disclosure selector from `scripts/lib/lang-selector.mjs`
(button + menu, not a row of two-letter codes). Polish, Swedish, Danish and
Simplified Chinese joined PT/EN/NL/FR/DE in September 2026; five codes on one
row already wrapped on a phone, nine would not have been tappable.

The Dutch cluster is generated by `scripts/generate-nl-cluster.mjs` from
`scripts/nl-cluster.data.mjs`. For most of that generator's life the language
switcher was a *local* template: a pipe-separated `PT | EN | NL | FR | DE`
row, baked into the HTML it wrote. Regenerating the cluster therefore
re-emitted the old control onto every previously-published `/nl/…` page,
undoing whatever `lang-switcher.mjs` (or a later hand edit) had put there.

That is not a 404 and not a failed test. It is a published-file / generator
divergence: the live pages were ahead of the generator, and the generator
is what anyone running `node scripts/generate-nl-cluster.mjs` actually
executes.

### Why the workaround was used

This happened three times in the cluster-completion work. Each time the
intended commit was a narrow content change (a privacy-URL alignment, a new
satellite page, a hub link). Regenerating to pick up that change also
rewrote the lang-switcher markup on every previously-published page in the
cluster. Committing the whole regen would have mixed a chrome rewrite into a
content commit, against "one logical change per commit".

The workaround, each time: inspect `git diff --stat` after the regen, revert
the lang-switcher hunks on the already-published pages, keep only the
intended content, and ship. That keeps the commit scoped. It also means the
next person who regenerates the cluster — without this conversation in their
head — gets the whole lot back in one commit.

### What a proper fix would involve

One writer. The cluster generator has to emit the selector from
`scripts/lib/lang-selector.mjs`, the same module `lang-switcher.mjs` uses,
with the same pair map and the same indentation, so a regen is a no-op on
the control. `lang-switcher.mjs` stays the canonical pass for the rest of
the site; the generator's job is to not fight it.

That is *not* "run `lang-switcher.mjs` after every NL regen and call it
done". A two-pass pipeline where the second pass exists to undo the first
is how this drifted in the first place.

Pair maps are the remaining sharp edge even after the markup is shared.
`generate-nl-cluster.mjs` currently builds targets from `page.hreflang.pt`
and `page.hreflang.en` only. `lang-switcher.mjs` builds them from the
article-cluster map *plus* `marketPairs()`. If those two sets ever disagree,
the generator will still rewrite the control on every page the next time it
runs, even though both now call the same HTML helper. A proper fix makes
the generator ask the canonical pair map, not a local subset.

### It is the NL cluster specifically

The Dutch cluster is the one that has been regenerated often enough, with
enough already-published pages, for this to keep resurfacing. The German
generator (`scripts/generate-de-cluster.mjs`) is the same shape and will
do the same thing the first time someone regenerates it against pages that
`lang-switcher.mjs` has since moved on. The EN blog articles are
hand-authored, not generated, so they only pick up the new control when
`lang-switcher.mjs` is run against them (or when each file is edited by
hand). New EN/DE/NL pages cut on `content/cluster-completion` before the
market-expansion merge landed still shipped the five-code row; the merge
into `main` ran `lang-switcher.mjs` over those 23 new files so they did
not go live next to eight-language neighbours.

Verified on `main` after that merge, not assumed: `node
scripts/generate-nl-cluster.mjs` currently produces a zero diff against
the published `/nl/…` cluster pages. The market-expansion work
(`scripts/lib/lang-selector.mjs`, wired into the NL generator) closed the
markup gap. The pair-map gap above is still open. Do not take the zero
diff as "this cannot come back".

Not fixed in this branch. Recorded so the fourth regen is a known
operation, not a rediscovery.

## Sitemap priority: `/nl/` and `/fr/` still at 0.8

Spotted while comparing `/nl/` and `/nl/verzekeringen-portugal/` as
competing hubs; recorded here, not changed.

`scripts/generate-sitemap.mjs` `priorityFor()` gives `1.0` to `/`, `/en/`,
`/de/`, `/pl/`, `/se/`, `/dk/` and `/zh/`. `/nl/` and `/fr/` fall through
to the default `0.8`. The comment in that function says this is on
purpose: `/nl/` is treated as a single landing whose cluster hangs off
sibling URLs rather than off it, and `/fr/` is one page.

That comment is now the interesting part, not an oversight to silently
"correct". After the market expansion, `/pl/`, `/se/`, `/dk/` and `/zh/`
are full clusters and sit at `1.0` with `/de/`. `/nl/` is also a full
cluster — sixteen pages plus `/nl/` itself — and is the one language
homepage still at `0.8` alongside `/fr/` (which really is one page).
`/nl/verzekeringen-portugal/` is also `0.8`, so the two Dutch URLs are
tied with each other and behind every other language homepage except
French.

Changing either value is a crawl-budget decision, not a bugfix. Leave
both at `0.8` until someone decides `/nl/` should be weighted as a
language homepage the way `/de/` is.
